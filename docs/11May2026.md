## FastMCP state management with context
Store and share data between middleware and handlers within a single MCP request. Each MCP request (such as calling a tool, reading a resource, listing tools, or listing resources) receives its own context object with isolated state. Context state is particularly useful for passing information from middleware to your handlers. To store a value in the context state, use ctx.set_state(key, value). To retrieve a value, use ctx.get_state(key).
Context state is scoped to a single MCP request. Each operation (tool call, resource read, list operation, etc.) receives a new context object. State set during one request will not be available in subsequent requests. For persistent data storage across requests, use external storage mechanisms like databases, files, or in-memory caches.
This simplified example shows how to use MCP middleware to store user info in the context state, and how to access that state in a tool:

```python
from fastmcp.server.middleware import Middleware, MiddlewareContext

class UserAuthMiddleware(Middleware):
    async def on_call_tool(self, context: MiddlewareContext, call_next):

        # Middleware stores user info in context state
        context.fastmcp_context.set_state("user_id", "user_123")
        context.fastmcp_context.set_state("permissions", ["read", "write"])

        return await call_next(context)

@mcp.tool
async def secure_operation(data: str, ctx: Context) -> str:
    """Tool can access state set by middleware."""

    user_id = ctx.get_state("user_id")  # "user_123"
    permissions = ctx.get_state("permissions")  # ["read", "write"]
    
    if "write" not in permissions:
        return "Access denied"
    
    return f"Processing {data} for user {user_id}"
```
Method signatures:

    ctx.set_state(key: str, value: Any) -> None: Store a value in the context state
    ctx.get_state(key: str) -> Any: Retrieve a value from the context state (returns None if not found)

State Inheritance: When a new context is created (nested contexts), it inherits a copy of its parent’s state. This ensures that:

    State set on a child context never affects the parent context
    State set on a parent context after the child context is initialized is not propagated to the child context

This makes state management predictable and prevents unexpected side effects between nested operations.

Executive Summary

Your "move everything to backend" philosophy is not the root problem — the root problem is that you have no architectural boundary at all. The frontend and backend aren't separated by a clean contract; they're separated by an ad-hoc pile of stringly-typed JSON mutations. Every new feature has to touch 4–6 unrelated files (App.tsx, ws-client, server router, handlers.rs, settings.ts, sometimes acp-client.ts), and none of those files have type safety or tests. That's why each feature spawns three bugs.

The most broken component is the RPC/state boundary. Fix that first and everything else accelerates.
The Diagnosis
1. App.tsx is a 1,481-line God Object

It owns: workspace root, open files, dirty tracking, FlexLayout model, explorer visibility, cursor position, word wrap state, agent config, menu state, save status, terminal/chat minimization, keyboard shortcuts, auto-restore logic, and tab lifecycle.

Why this kills you: Every feature needs state. Since all state lives in one component, every feature touches the same file. Refs are used to avoid stale closures in a component that re-renders constantly. Effects are layered on effects to sync React state with FlexLayout's imperative model.

The bug pattern: You add a feature that needs layout state → you mutate layoutModelRef inside a callback → React doesn't know → you add another useEffect to sync it back → that effect fires at the wrong time → bug.
2. The RPC Layer is Untyped Spaghetti

// frontend
ws.invoke("document_open", { path, content })

// backend
pub fn handle_document_open(state: &AppState, params: &Value) -> Result<Value, String> {
    let path = params["path"].as_str().ok_or("missing 'path'")?;

This is your entire API contract. No schema, no generated types, no validation. If you rename a field, you find out at runtime. If you forget a param, you get "missing 'path'". If the backend returns { entries: [...] } but the frontend expects an array, you get a silent failure (which I see happened with get_recent_workspaces).

Why this kills you: You can't refactor safely. Changing anything in handlers.rs requires manually auditing every ws.invoke() in the frontend. You will always miss one.
3. Two WebSockets Doing the Same Job

You have:

    /ws — app control (documents, files, terminals, settings)
    /ws/acp — "dumb pipe" for ACP

But /ws/acp is not a dumb pipe. It has its own handle_acp_message, its own request/response IDs, its own pendingRequests map in AcpClient. Meanwhile, the app WebSocket also handles ACP control commands (acp-command-new-session). The ACP client duplicates half of WsClient's logic.

Why this kills you: Connection management, reconnection, and error handling are duplicated and subtly different. When one drops, the other doesn't know. The frontend maintains two separate pending-request maps with two separate ID spaces.
4. Settings Are Schizophrenic

You have three settings systems:

    crow-ui-settings crate (Rust) — layered store with user/workspace layers, proper lookup, JSONC persistence
    frontend/src/lib/settings.ts — frontend cache with DEFAULT_SETTINGS object that must be kept in sync with Rust
    SettingsPane.tsx — reads/writes ~/.crow/murder.json directly via write_file/read_file, bypassing the backend settings system entirely

Why this kills you: SettingsPane writes to the legacy path (murder.json), then calls settings.loadSettings(), which fetches from the backend... which reads from crow-ui-settings.json. The backend has a migration from murder.json, but the frontend is still writing to it. The getConfigPath handler returns ~/.crow/murder.json, cementing the confusion.
5. Document State Lives in Two Places (Badly)

    Monaco model registry (frontend, module-level Map)
    TextModel in AppState.documents (backend, DashMap)

When the agent writes a file, the backend updates its TextModel, emits a worktree-file-changed event, and the frontend calls setModelContent(), which updates the Monaco model. When the user types, Monaco fires onDidChangeContent, and... the frontend does not call document_edit for every keystroke. It only sends content at save time via document_set_content.

Why this kills you: The backend TextModel version increments on document_edit, but the frontend rarely sends edits. The backend thinks it has the authoritative document model, but it's actually stale until save. Meanwhile, acp_read_file returns the backend model's content (which is stale) instead of the Monaco model's content. You have a getModelContent() escape hatch in acp-client.ts for readTextFile, but not for the backend's own read_file handler.
6. Backend Crates Are Disconnected Islands

You have crates for:

    crow-ui-lsp — completely unwired
    crow-ui-git — completely unwired
    crow-ui-syntax — completely unwired
    crow-ui-theme — completely unwired
    crow-ui-textmate — completely unwired

They exist in Cargo.toml but handlers.rs has zero references to them. The server only knows about documents, files, terminals, ACP, DB, and settings.

Why this kills you: You're paying the compile-time cost of a modular architecture without getting any of the benefits. There's no plugin boundary, no capability system. When you want to add git status to the explorer, you have to bolt it onto the existing mess rather than wiring up an existing crate.
7. No Observability Anywhere

    Backend has tracing configured but only logs WebSocket connect/disconnect and serialization errors.
    Frontend has a debug.ts that logs to console only if localStorage.debug === "1".
    No request logging (you don't know what RPC calls are failing).
    No frontend error reporting to backend.
    No metrics on handler latency.

Why this kills you: You can't tell if a bug is in the frontend, the backend, or the network. When something fails, you add console.log and rebuild.
8. Zero Tests in Production Code

I found no frontend tests and no backend tests outside of crow-ui-textmate and crow-ui-settings (which have unit tests for their internal logic). The server, the WebSocket protocol, the document sync, the layout restore — none of it is tested.

Why this kills you: Every refactor is a leap of faith. You can't change the RPC format without manually clicking through every feature.
The "Backend vs Frontend" Philosophy Question

You asked if "move everything to backend" is viable for a FlexLayout React app. My answer: partially, but you're doing it wrong.

Things that should live in backend:

    File I/O (obviously)
    Process management (terminals, ACP agents)
    Durable persistence (settings, layout DB, recent workspaces)
    Search/indexing
    Git operations
    LSP protocol handling

Things that must live in frontend:

    FlexLayout model state (it's a React library; fighting it is futile)
    Active/selected tab state
    Editor view state (scroll position, cursor, selections)
    Which files are open (the "working set")
    Transient UI state (context menus, modals, toasts)

Things that should be owned by backend but cached in frontend:

    Document content (backend is source of truth, frontend renders it)
    File tree (backend scans, frontend renders)
    Settings (backend persists, frontend reads on load)

Your current mistake: You're trying to put FlexLayout state in backend SQLite (the save_workspace_layout / get_workspace_layout dance), which creates an impedance mismatch. FlexLayout owns its model. You can serialize it for restore, but the runtime state must live in React.
The Fix: Priority Order
Phase 1: The Keystone — Typed RPC + Frontend State Decoupling

This is the component to tackle first. Everything else is blocked on it.

    Define the API schema in one place. Use something like or hand-write TypeScript interfaces + Rust structs. Every RPC method gets a Request/Response type pair.
    Generate or share types. The frontend should import request/response types. The backend should deserialize into structs, not serde_json::Value.

    Refactor App.tsx into domain stores. Create:
        useWorkspace() — workspace root, file tree, recent files
        useEditor() — open files, dirty state, active file
        useLayout() — FlexLayout model (this stays in React)
        useSettings() — settings cache + backend sync
        useTerminalManager() — terminal lifecycle
        useAcp() — agent sessions

    Each store owns its slice of state. App.tsx becomes a shell that composes them.

    Add request logging. In ws-client.ts, log every invoke with its method, payload size, and duration. In ws.rs, add a tracing::info! for every incoming request with its ID and method. Add a request_id field that flows both ways.

Phase 2: Kill the Dual WebSocket

Move ACP traffic onto the main /ws connection. Add a multiplexing layer:

ws.invoke("acp_spawn", {...})  // goes to AgentManager
ws.onAcpEvent((agentId, msg) => ...) // subscribes to agent broadcasts

This eliminates AcpClient's duplicated WebSocket logic and lets you use a single reconnect strategy.
Phase 3: Fix Settings First (Self-Contained Domain)

Settings is the perfect place to prove the pattern because it doesn't touch FlexLayout.

    Delete SettingsPane's direct file I/O. It should call update_setting for individual keys, not write a JSONC blob.
    Unify the settings path. The backend owns ~/.crow/crow-ui-settings.json. The frontend never knows the path.
    Remove DEFAULT_SETTINGS from frontend. The frontend calls get_all_settings on boot and gets the fully resolved nested object from the backend. No drift.
    Add settings validation. When the backend loads, validate the user layer against a schema. Log warnings for unknown keys.

Phase 4: Document Sync Protocol

Decide who owns the document:

    Option A (recommended): Backend is source of truth. Frontend sends incremental edits (document_edit) on every change. Backend broadcasts changes to other listeners.
    Option B: Frontend is source of truth for open documents. Backend is only for save/load.

Currently you're doing Option B but pretending it's Option A. The backend TextModel is a ghost. Either wire up incremental sync properly, or simplify: remove documents from AppState and have the backend be a dumb file server. (Given you want LSP eventually, Option A is better long-term.)
Phase 5: Wire Up the Dead Crates

Once the RPC boundary is clean, wiring up crow-ui-git or crow-ui-lsp becomes trivial: add a handler, add a frontend hook, done. Right now it would be surgery.
Immediate Practices to Adopt
Practice	Why
No serde_json::Value in handlers	Force struct definitions; catch mismatches at compile time
No ws.invoke("string", {...})	Use typed wrappers: documentApi.open({ path })
No module-level state in frontend	modelRegistry, openedDocuments, sessions Map — all of these hide state from React. Use Zustand or at least context.
Log every RPC call with timing	tracing::info!(id, method, elapsed_ms) in backend; console.log("[RPC]", method, duration) in frontend
Frontend error telemetry	Add window.onerror + window.onunhandledrejection that send to backend via log_error RPC
Tests for the RPC boundary	Even one test that spins up the server, connects a WS, and calls document_open would prevent 50% of your bugs
Bottom Line

The project isn't failing because you put too much in the backend. It's failing because there is no contract between frontend and backend, so every feature requires manual coordination across 1,500-line files with no type checking or tests.

Tackle the RPC boundary and App.tsx decoupling first. That is the keystone. Once you have typed RPC and domain-specific state hooks, adding git status, LSP, or a new panel becomes a 20-minute task instead of a 3-day bug hunt.
